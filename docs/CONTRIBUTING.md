# 협업 규칙
## 브랜치
통합 대상은 b2-2이며 feature/<계정>-<작업>에서 변경한다.
GitHub Flow를 사용해 변경 단위를 작게 유지하고 이슈와 PR로 추적한다.
공유 브랜치의 강제 push, reset, rebase는 사용하지 않는다.

## 커밋
형식은 `type(module): English description`이다.
feat, fix, docs, test, chore 등을 사용하고 module에는 변경 대상을 적는다.
update, temp, final처럼 변경 내용을 알 수 없는 메시지는 사용하지 않는다.
여러 파일을 바꾸면 작업 의도와 세부 사항을 한국어 개조식으로 기록한다.

## 이슈와 PR
각 작업의 이슈를 먼저 만든다. PR 제목은 `(계정): 변경 내용`이다.
PR 본문에는 What, Why, How 및 `Closes #번호`를 포함한다.
대상은 b2-2다. 기본 브랜치가 아니므로 자동 종료에 의존하지 않고 병합 확인 후 이슈를 종료한다.

## 검토
파일과 근거가 있는 질문 또는 개선 제안을 댓글로 남긴다.
변경 작성자는 수정 커밋과 답글로 반영 결과를 남긴다.
제목의 역할 이름과 GitHub가 표시하는 실제 작성 계정을 구분한다.
독립된 승인자가 없으면 approve 요건을 충족했다고 기록하지 않는다.

## 충돌
통합 브랜치를 작업 브랜치에 merge하고 git status로 충돌 파일을 확인한다.
양쪽 변경의 의도를 비교해 해결한 뒤 검사하고 커밋한다.
docs/conflict-resolution.md에 명령, 충돌 마커, 선택 이유, 결과 SHA를 기록한다.
