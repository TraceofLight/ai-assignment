# 사전평가 보완 문답과 근거 색인

[과제 README로 돌아가기](../README.md)

2026-09-19 사전평가의 15개 항목을 기준으로 주 에이전트와 읽기 전용 검토 서브에이전트가 실제 저장소의 README, 스키마, 시드, 쿼리, 실행·검증 스크립트를 읽고 주고받은 문답을 정리했다. 아래 합의는 평가 점수나 통과를 보장하는 판정이 아니라 수정 범위와 검증 기준이다.

## 1. 기존 설명을 다시 쓰는 것이 필요한가?

**질문:** 평가에는 설명이 없다고 되어 있는데, 현재 README에는 타입·관계·JOIN·집계 설명이 이미 있다. 모두 새로 작성해야 하는가?

**검토 답변:** 현재 파일에는 상당한 설명이 있으므로 평가문만으로 현재도 누락되었다고 단정할 수 없다. 같은 내용을 복제하기보다 평가 항목과 기존 설명을 연결하고, 부족한 정규화·PK/FK 구분·샘플 선정 이유·실행 화면을 보완하는 것이 직접적이다.

**합의:** 기존 README를 보존하면서 필요한 설명을 확장하고 아래 근거 색인으로 확인 위치를 제공한다.

## 2. Q10과 Q12는 정말 같은 결과인가?

**질문:** 둘 다 고객별 결제 매출을 계산하므로 같은 요구를 다른 방식으로 풀었다고 해도 되는가?

**검토 답변:** 원본 시드 기준 Q10은 결제 완료 주문 상세가 있는 고객 8명만 반환한다. Q12는 모든 고객 10명을 반환하고, 결제 완료 주문이 없는 고객 5번 정도윤과 10번 한예린을 `COALESCE`로 0원 처리한다. 공통 고객의 금액은 같지만 포함 범위가 다르다.

**합의:** 기존 SQL 결과를 바꾸기보다 주석과 설명에서 결과 포함 범위 차이를 명시한다. 상관 서브쿼리의 성능 우열은 측정 없이 단정하지 않는다.

## 3. DATE와 1:N 선언만으로 무엇이 보장되는가?

**질문:** `DATE`는 날짜 유효성을, 1:N 관계는 부모마다 자식이 하나 이상 있음을 보장하는가?

**검토 답변:** SQLite의 `DATE`·`DATETIME` 선언만으로 날짜 형식이나 달력상 유효성이 강제되지는 않는다. 이 과제는 일정한 ISO 형식의 문자열을 저장한다. 또한 현재 FK와 `NOT NULL`은 각 자식이 존재하는 부모 하나를 참조하도록 하지만, 부모마다 자식이 존재하도록 하지는 않는다. 부모의 자식 수는 0..N이다.

**합의:** 타입 선택 의도와 실제 강제 범위를 구분한다. 주문 상세가 하나도 없는 주문까지 스키마가 차단한다고 설명하지 않는다.

## 4. 시드를 바꾸지 않고 LEFT JOIN의 차이를 증명할 수 있는가?

**질문:** 원본 시드에서는 모든 고객이 주문을 가지고 있는데, 주문 없는 고객을 보여주려면 샘플 고객을 추가해야 하는가?

**검토 답변:** Q15가 주문 112를 삭제한 뒤에는 고객 10번 한예린에게 주문이 없다. 이 상태에서 고객별 주문 수를 집계하면 LEFT JOIN은 한예린 0건을 포함한 10행, 동일 조건의 INNER JOIN은 한예린을 제외한 9행이 된다.

**후속 질문:** 그러면 모든 쿼리를 Q15 이후 DB에서 다시 실행해 캡처해도 되는가?

**검토 답변:** Q14·Q15가 데이터를 변경하므로 앞선 텍스트 결과와 달라질 수 있다. 핵심 쿼리는 초기화된 DB에서 Q01→Q15 순서대로 실행하고, 추가 JOIN 비교는 Q15 실행 후라는 상태를 별도로 밝혀야 한다.

**합의:** 원본 시드를 유지하고 보충 SQL·결과·캡처의 이름과 실행 상태를 구분한다. 실행 화면은 SQL과 실제 결과를 확인할 수 있어야 하며, 텍스트를 이미지로 꾸민 자료를 실제 클라이언트 캡처라고 제시하지 않는다.

## 5. 주문 당시 단가는 정규화 위반인가?

**질문:** 정규화 설명에 테이블별 함수 종속과 주문 당시 단가 보관 이유를 제시하면 충분한가? 현재 메뉴 가격과 주문 단가가 같다면 중복 아닌가?

**검토 답변:** 먼저 `menu_item_id` 하나가 모든 주문의 `unit_price`를 결정하는지 물어야 한다. 가격은 주문 시점이나 적용 조건에 따라 달라질 수 있다. `menu_item.price`는 현재 판매 가격이고 `order_item.unit_price`는 해당 상세에 실제 적용한 과거 단가이다. 시드에서 두 값이 같다는 사실만으로 동일 속성의 불필요한 중복이라고 볼 수 없다.

**합의:** 고객 ID→고객 속성, 주문 ID→고객·담당 직원·시각·상태, 상세 ID→주문·메뉴·수량·당시 단가 등 업무상 가정한 종속을 설명한다. 대체 PK가 있다는 사실만으로 3NF가 자동 증명된다고 쓰지 않는다. 메뉴 가격 변경으로 과거 주문 매출까지 바뀌지 않도록 서로 다른 사실을 별도 저장한다는 이유를 명시한다.
